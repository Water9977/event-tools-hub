## 2026-08-05 — Research phase: micro-tool hub, event/party-planning theme selected

**Context.** User wanted to replicate a viral "₹4L/month solopreneur" video's micro-tool-website-for-AdSense playbook. Fact-checked the video first rather than building on it blind — two of its core claims didn't hold up under research (see below), and one 2026-specific fact it never mentions (AI Overviews) ended up being the single biggest factor in tool selection.

**What was checked and found false:**
1. AdSense approves pure tool/calculator sites easily — false. Google's own AdSense support forum (April 2026, community-recommended answer) confirms tool-based sites get rejected for "low value content," and finance-adjacent tool sites face "forever rejection." Fix adopted: every tool ships with genuine 1200+ word original content; finance/health/legal/insurance/tax/medical/salary tools excluded outright.
2. 12 separate domains is the right shape for "fastest, least investment" — false. 12 cold-start domains = 12 AdSense reviews, no compounding authority, 12x cost, and matches Google's named "multiple sites to hide scaled content abuse" spam pattern (March/June 2026 updates). Decided instead: one hub domain, tools as routes.

**Research pipeline built:** 6 subagent definitions (`opportunity-miner`, `serp-gap-analyst`, `aio-resistance-checker`, `monetization-analyst`, `build-feasibility`, `opportunity-synthesizer`) saved to `.claude/agents/` and mirrored into a reusable skill at `E:\Claude\Claude Skills\Micro Tool Research\`. **Environment note:** this session's harness didn't register project-level custom subagents (only 6 built-in types available: claude, claude-code-guide, Explore, general-purpose, Plan, statusline-setup) — the agent .md files exist for real Claude Code CLI use, but this session ran the same instructions through `general-purpose` agents instead. If a future session has real custom-subagent support, use the files directly per `Micro Tool Research/references/agent-setup.md`.

Ran wave 1 (opportunity-miner → 134 candidates) then wave 2 (4 parallel scoring passes) then synthesis in the main thread (not delegated — composite scoring needed judgment calls a fresh subagent wouldn't have context for). Full outputs in `research/01` through `research/05`, merged shortlist in `research/00-MASTER-SHORTLIST.md`.

**Headline finding:** the event/party-planning tool cluster (Tent Size Calculator, Party Budget Planner, etc.) scored best across every dimension — SERP gap, monetization, feasibility — AND uniquely, it's the only cluster tied to a domain the user already owns with live GSC impressions (eventrentalcosts.com, ~180 impressions across 15+ metros on tent/party/wedding-rental queries, 2-3 weeks old at research time). Chosen as the hub theme specifically because it inherits authority instead of cold-starting.

**Critical mid-research finding — most of the flagship cluster died to AI Overviews:**
The `aio-resistance-checker` agent used a phrasing-based proxy (task-completion phrasing = low risk, informational phrasing = high risk) drawn from Ahrefs' 2026 research. This proxy under-predicted risk for one specific pattern: **simple formula + lookup-table calculators, where the entire "task" is guest-count × a public per-person constant.** Manual live-Google verification (round 2-4 of the research session) found:
- Tent Size Calculator ("tent size calculator") — AI Overview renders the full space-guidelines table, common-tent-sizes table, sourced from the same competitor sites the SERP-gap agent found, AND offers to compute exact dimensions inline given a guest count. Originally the unanimous #1 pick across all 4 scoring agents — killed as a standalone traffic driver by this single check.
- Guest Count Estimator ("wedding guest calculator", "how many guests will RSVP calculator") — same failure, same mechanism (attendance-rate multiplier × invite count).
- Drink/Alcohol Calculator, Food/Catering Calculator — same failure, confirmed on the natural "how much X for a party" phrasing.
- **Party/Event Budget Planner — the one candidate that survived clean.** Reasoned root cause: budgeting has real free variables (income, priorities, vendor quotes already obtained) that don't reduce to one canonical inline answer Google can pre-compute.

**Revised heuristic adopted for all future candidate selection in this project:** the dividing line isn't task-vs-informational phrasing, it's whether Google can compute the *entire* answer from a public formula plus one number the user types into the search box. Formula+lookup-table calculators are AI-Overview-replaceable almost by construction. Interactive/stateful tools (drag-and-drop, paste-your-own-text/code, upload-a-file, multi-step/save-state) are not, because Google can't see or process the user's actual input inline.

**Build order locked** (see TODO.md for the live checklist): Budget Planner (flagship) → Tent Size Calculator (demoted to companion/internal-link role, still built because the underlying keyword-cluster synergy is real even though standalone AIO traffic isn't) → Wedding Seating Chart Planner (promoted — structurally AIO-immune, worth the extra build complexity) → Binary/Hex/Base64/URL Toolkit (fast, cheap, resistant, diversifies outside the event-only failure mode).

**Second independent research pass (Google Antigravity, different methodology on purpose):** surfaced a genuinely useful dev/visual-tool cluster (CSS box shadow generator, flexbox visualizer, etc.) this pipeline's competitor-sitemap mining never touched, since it only mined calculator/converter aggregator sites, not dev-tool hubs. Also produced a "Public Revenue Precedents" section (specific $/month figures attributed to Indie Hackers/Show HN posts) with **zero source links or post citations despite the prompt explicitly requesting them** — treated as unverified/likely-fabricated and discarded. Real, useful signal from a second research pass (dev-tool candidate ideas) doesn't imply every section of that pass is trustworthy; each claim was checked independently rather than accepted wholesale.

**Verified live keyword data (Ahrefs free generator, human-pasted, round 2):** "tent rental cost" — 101 keyword variants, several breaking into the >100 volume bucket, Easy KD, same cluster eventrentalcosts.com already has real GSC impressions on. This is the actual money cluster; "tent size calculator" itself is real but small (<100 vol every variant). This is the evidence behind treating Tent Size Calculator as a companion/internal-link page rather than its own traffic bet, and behind defaulting to a subdomain of eventrentalcosts.com rather than a fresh domain (open decision, defaulted not yet confirmed — see TODO.md).

**Nothing built yet as of this entry.** Next session/step: scaffold the Astro project, decide subdomain vs. domain for real (currently defaulting to subdomain), build Party/Event Budget Planner first.

**Party/Event Budget Planner built**, per the locked build order: event-type selector (wedding/birthday/corporate/casual) with per-category dollar defaults computed from percentage presets, live-editable category amounts, running-total vs. budget indicator (on-budget/under/over), localStorage auto-save, print button, 1200+ word guide content, 5-question FAQ with JSON-LD schema.

**Content sourcing, not fabrication.** Before writing the guide content, searched for real wedding-budget-percentage data rather than inventing plausible-looking numbers. The birthday/corporate/casual presets don't have a comparably-sized public dataset, so those are labeled in the copy as "general planning heuristics," not presented as data-backed — matches the project's own "real data only, never present a guess as verified fact" standard from the research phase.

**Verification trail (real testing, not "should work"):**
1. `npm run build` — clean, 7 pages, no errors.
2. Live browser test via `npm run dev`: event-type switching, live category editing, over/under-budget math, localStorage save — all confirmed working correctly through real interaction, not just visual inspection.
3. **Found and root-caused a real bug via testing, not guessed at:** `npm run dev` (Cloudflare adapter's local Miniflare simulation) started throwing 500s on every request after a resize+reload. Did NOT guess-patch. Checked the actual console/server error (`Unable to fetch the Request.cf object`, then `TimeoutError`/`fetch failed` to `workers.cloudflare.com`), searched for the exact error, found [cloudflare/workers-sdk#3460](https://github.com/cloudflare/workers-sdk/issues/3460) confirming this is a known Miniflare behavior (it's supposed to fall back to a placeholder cleanly, like it does during `build`, but the dev-mode Vite plugin cascades the same failure into full request errors instead) — a sandbox-networking/dev-tooling issue, not a defect in this project's code.
4. **Root cause confirmed by testing the actual production artifact instead:** since `output: 'static'`, Cloudflare Pages serves the static build directly with no Workers runtime — so tested `dist/` served by a plain static server instead of fighting the dev-mode simulation. **Second real bug found this way, also root-caused before fixing:** initially served `dist/` directly with `npx serve`, got 404s on every route — checked the actual filesystem rather than guessing, found the Cloudflare adapter nests static output under `dist/client/` (with `dist/server/` alongside it for the Workers entrypoint, unused in static mode) even when `output: 'static'` is set. Fixed by serving `dist/client`, confirmed all routes (`/`, `/about/`, `/contact/`, `/privacy-policy/`, `/terms/`, `/party-budget-planner/`) return real 200s and an unknown path returns the custom 404 page. Also separately found and fixed a bad `serve -s` (SPA rewrite mode) flag that was wrong for this multi-page static site.
5. Mobile viewport (375px) checked for real horizontal overflow via `document.documentElement.scrollWidth` — none.
6. Dark mode toggle checked bidirectionally via direct DOM/localStorage inspection (the `computer` click tool hung on this specific harness — worked around by dispatching the click via JS and checking real state, not by trusting the click "should have" worked).

Both root-caused issues (Miniflare's `workers.cloudflare.com` dependency, and the `dist/client` nesting) are logged in TODO.md under "Known environment quirk" so a future session doesn't waste time rediscovering them.

## 2026-08-05 (session 3) — Design pass: matched the sibling site's palette, found and fixed two real CSS bugs

**Design system sourced, not guessed.** User asked to scrape eventrentalcosts.com and use its local source (`E:\Claude\Workspaces\Niche Directory\website`) so the two sites look related. Read the sibling's actual `global.css`/`BaseLayout.astro`/`Header.astro`/`Footer.astro`/`ThreeStateBadge.astro`/`index.astro` directly rather than trusting a live-page scrape alone — the scrape's automated `branding` extraction got two things wrong (said font was literally "Roboto" when it's a system-font stack with Roboto as one fallback; said border-radius was `0px` when the real values are 6/10/16px). Wrote `DESIGN.md` from the code, used the scrape only for the screenshot and as a secondary cross-check. Full findings and exact token values in `DESIGN.md`.

**Dark mode decision:** user said "include dark mode too if its the need" — kept dark mode (reasonable for a calculator someone uses at night) but built it as a brand-consistent warm-dark variant (same hue families as the light palette, adjusted for contrast) rather than a generic slate swap, so it doesn't read as a different product at night. Light mode matches the sibling site's palette exactly.

**Implementation:** Tailwind v4 CSS-first tokens via `@theme inline` (required specifically because the theme values need to track runtime CSS custom properties that change with the `.dark` class — plain `@theme` bakes in static values, `@theme inline` keeps the `var()` indirection). Runtime vars defined in `:root` (light) and `:root.dark` (dark overrides).

**Bug #1, found and root-caused via testing, not assumed:** `.card`'s border-color wasn't updating with the dark-mode toggle, even though background/text colors on the same element updated correctly. Isolated it methodically: an inline-style test element resolved the same CSS variable correctly, proving the variable itself was fine; inspecting the live stylesheet rules showed Astro compiles each component's scoped `<style>` block to plain, unlayered CSS. Per the CSS Cascade Layers spec, unlayered rules always beat layered rules regardless of specificity or source order — so wrapping `.card` in `@layer components` made it unconditionally lose to Astro's scoped styles on any element carrying a `data-astro-cid-*` attribute (i.e. every component-scoped element on the site). Fix: stopped using `@layer base`/`@layer components` for shared classes entirely, matching what the sibling site's own CSS actually does (no `@layer` wrapping there either) — confirmed the fix worked via the same computed-style check that found the bug, not just by reasoning that it should.

**Bug #2, same investigation session:** even after fixing bug #1, toggling dark mode via the real toggle button (not raw class manipulation) still left `.tool-card`'s border-color stuck on the light value — but only light→dark, not dark→light, and not on a fresh page load with dark already active. Considered and ruled out a testing-artifacns theory first (reading computed style synchronously might catch a CSS transition mid-animation) by re-testing with an explicit 300ms wait — the stuck value persisted, proving it wasn't a timing artifact of the test itself. Root cause: `.tool-card` had `transition: border-color 150ms ease` for its hover effect, and CSS transitions can fail to correctly re-trigger when the underlying change comes from a `:root`-level custom property update rather than a direct property change on the transitioning element — a known problematic pattern, not a one-off browser quirk. Fix: removed the transition (an instant hover border-color change is fine UX), and proactively removed the same pattern from `.btn`/`.btn-secondary` since they had the identical shape (color driven by a theme-swapped custom property, with a transition on that property) even though a bug hadn't been observed there yet — confirmed by checking the sibling site's actual CSS, which has no transitions on its hover color changes either. Both fixes logged in TODO.md under "Known CSS gotcha" with the exact mechanism, so a future session doesn't have to rediscover this.

**Also fixed in passing:** `@tailwindcss/typography` (needed for every `prose` class used across the legal pages, About, and the Budget Planner's guide content) was never actually installed in session 2 — the `prose` classes had been silently doing nothing since the site was first scaffolded. Installed and registered via `@plugin "@tailwindcss/typography"` in `global.css` (Tailwind v4's CSS-first plugin syntax).

**Built the real homepage** (was still Astro's scaffold placeholder) — hero section matching the sibling's subtle-gradient pattern, a tool card grid (currently one real card, Party Budget Planner; intentionally not implying more tools exist than do).

**`npm install` surfaced 5 `npm audit` findings** (4 moderate, 1 high) in `undici`, transitive through wrangler/miniflare/`@astrojs/cloudflare`'s dev-time tooling — not shipped in the production static build, not a runtime risk to the deployed site. Fixing requires a breaking wrangler major-version bump; didn't do this reactively mid-task, logged in TODO.md to revisit deliberately.

**Verification, same standard as session 2:** every claim in this entry was checked via real `getComputedStyle` reads in an actual browser against the actual built static output (`dist/client`, same lesson from session 2 about where the real static files live), not inferred from source code alone. Both directions of dark-mode toggle re-tested after each fix. All routes re-confirmed 200/404 as expected. Mobile viewport re-confirmed no horizontal overflow.
